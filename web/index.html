¿Qué es CS Interactive Lab?

Un laboratorio en el navegador donde los temas difíciles de computación se ven, se oyen y se tocan. En vez de leer sobre un deadlock, lo provocas. En vez de memorizar Big-O, ves la diferencia.

2

¿Para quién es?

Para estudiantes de Ciencias de la Computación, en especial de la ECCI de la UCR, que están llevando algoritmos, programación concurrente, redes o bases de datos, o que se preparan para entrevistas técnicas. También para cualquier curioso.

3

¿Qué puedo hacer aquí?

Escoges una mesa de trabajo (un curso o tema) y luego una estación. Cada estación tiene tres pasos:

  • Experimenta: una simulación, o un depurador que recorre el código línea por línea.
  • Entiende: la idea detrás, explicada simple.
  • Implementa: código y consejos para tu proyecto.
4

¿Qué voy a aprender?

  • Algoritmos y estructuras: 8 ordenamientos compitiendo; pilas, listas y árboles.
  • Concurrencia: hilos, mutex y semáforos en una rotonda.
  • Redes: sockets TCP, HTTP y un servidor con pool de hilos.
  • Entrevistas: dos punteros, intervalos y ventanas deslizantes, de nivel medio a difícil.
  • Bases de datos: SQL ejecutado cláusula por cláusula.
5

¿Tengo que instalar algo?

No. Todo corre en tu navegador. Si quieres ir más lejos, el repositorio incluye los motores originales en C y C++ para compilarlos en tu máquina.

Consejos

                
    
                  
  • Prueba siempre con arreglos vacíos, de un elemento, repetidos e invertidos.
    • 
                  
  • En Quick Sort, usa un pivote aleatorio o la mediana de tres para evitar el O(n²).
    • 
                  
  • Para n pequeño (≈16), cambiar a Insertion Sort acelera los algoritmos recursivos.
    • 
                  
  • Cuenta comparaciones e intercambios en tus pruebas: es la forma más clara de verificar la complejidad.
    • 
                

              

              

                
En la vida real

                
    
                  
  • std::sort usa Introsort: Quick + Heap + Insertion.
    • 
                  
  • std::stable_sort se basa en Merge Sort.
    • 
                  
  • Python y Java (objetos) usan Timsort, un híbrido de Merge e Insertion.
    • 
                  
  • Para enteros de tamaño fijo, Radix Sort puede ganarle a todos.

¿Por qué se traba la rotonda?

                
Cada auto es un hilo y cada cuadrante es un recurso. Un deadlock aparece solo si se cumplen las cuatro condiciones de Coffman al mismo tiempo:

                
    
                  
  1. Exclusión mutua: en un cuadrante cabe un número limitado de autos.
    2. 
                  
  2. Retener y esperar: un auto ocupa su cuadrante mientras espera el siguiente.
    3. 
                  
  3. Sin expropiación: nadie puede sacar un auto de la rotonda a la fuerza.
    4. 
                  
  4. Espera circular: A espera a B, B a C, C a D… y D espera a A.
    5. 
                

                
La soluciónUn semáforo de entrada que nunca deja que la rotonda se llene por completo rompe la espera circular: siempre queda un hueco para avanzar.

              


              

                pthread_mutex_t
                
Mutex

                
La llave de un baño: una persona a la vez, y quien la toma la devuelve.

                
Protege secciones críticas cortas. Tiene dueño: solo el hilo que hizo lock puede hacer unlock.

              


              

                sem_t
                
Semáforo

                
Un parqueo con N espacios: si hay campo entras, si no esperas.

                
Un contador sin dueño. Sirve para limitar capacidad y para que un hilo le avise a otro.

              


              

                pthread_barrier_t
                
Barrera

                
El guía del tour: nadie sigue hasta que llegue todo el grupo.

                
Sincroniza fases. La simulación de calor la usa para que ningún hilo empiece la iteración siguiente antes de tiempo.

              


              

                _Atomic
                
Atómicos

                
Un torniquete: avanza de un clic, sin candados.

                
Operaciones que el procesador hace de una sola vez. Ideales para contadores y banderas compartidas.

              

            

          


          

            

              

                
La rotonda en C, simplificada


// Compila con: gcc -std=c11 -pthread rotonda.c
#include <pthread.h>
#include <semaphore.h>

#define QUADRANTS 4
#define CAPACIDAD 2                  // autos por cuadrante
int recorrido = 2;                    // cuadrantes que avanza cada auto
sem_t entrada;                       // cupo total de la rotonda
sem_t cuadrante[QUADRANTS];          // capacidad de cada cuadrante

void* auto_hilo(void* arg) {
  int q = *(int*)arg;                   // cuadrante de entrada
  sem_wait(&entrada);                  // nunca se llena del todo
  sem_wait(&cuadrante[q]);
  for (int i = 0; i < recorrido; ++i) {
    int sig = (q + 1) % QUADRANTS;
    sem_wait(&cuadrante[sig]);         // pide el siguiente…
    sem_post(&cuadrante[q]);           // …y suelta el actual
    q = sig;
  }
  sem_post(&cuadrante[q]);
  sem_post(&entrada);
  return NULL;
}

int main(void) {
  sem_init(&entrada, 0, QUADRANTS * CAPACIDAD - 1);  // la clave: -1
  for (int i = 0; i < QUADRANTS; ++i) sem_init(&cuadrante[i], 0, CAPACIDAD);
  /* crear hilos con pthread_create, esperarlos con pthread_join */
}

              

              

                
Consejos

                
    
                  
  • Toma los recursos siempre en el mismo orden. Es la forma más sencilla de evitar deadlocks.
    • 
                  
  • Mantén las secciones críticas cortas: nada de printf ni E/S con un mutex tomado.
    • 
                  
  • Cada sem_init y pthread_mutex_init lleva su destroy.
    • 
                  
  • Nunca uses espera activa (while(!listo);): bloquea con un semáforo o una variable de condición.
    • 
                

              

              

                
Para depurar

                
    
                  
  • Compila con -fsanitize=thread para detectar condiciones de carrera.
    • 
                  
  • valgrind --tool=helgrind ./prog encuentra errores de sincronización.
    • 
                  
  • Si sospechas de un deadlock, adjunta gdb y mira dónde está cada hilo con thread apply all bt.
    •

¿Qué acabas de ver?

                
Dos programas en dos computadoras: el cliente pide una figura y el servidor la busca en su disco y la devuelve. Por debajo hay dos protocolos trabajando juntos: TCP se encarga de que los bytes lleguen completos y en orden, y HTTP define qué dicen esos bytes.

                
La vida de un socket en el servidor

                
socket()bind(1234)listen()accept()Read / WriteClose()

                
El cliente solo hace socket() → connect() → Write → Read → Close().

              

              

                
El saludo de tres vías

                
"¿Me oyes?" "Sí, ¿y tú a mí?" "Sí." Y ya pueden hablar.

                
SYN, SYN-ACK y ACK sincronizan los números de secuencia de ambos lados. Desde ahí, cada byte enviado tiene un número, y el ack dice "ya recibí todo hasta aquí".

              

              

                
Anatomía de HTTP

                
Un mensaje HTTP es texto plano: una primera línea (método y ruta, o código de estado), encabezados Nombre: valor, una línea vacía y después el cuerpo. Cada línea termina en \r\n.

                
Tu servidor no envía Content-Length en las figuras: el cliente sabe que terminó cuando el servidor cierra la conexión (Connection: close).

              

              

                
Un hilo por cliente

                
Cada cliente que entra recibe su propio mesero.

                
El hilo principal solo hace accept(). Por cada conexión crea un std::thread(task, client) que lee, responde y cierra. Así un cliente lento no bloquea a los demás. Con miles de clientes conviene un pool fijo de hilos.

              

              

                
Segmentos y MSS

                
TCP no manda mensajes, manda un flujo de bytes partido en segmentos. En Ethernet con IPv6 cada segmento lleva como máximo 1440 bytes de datos (el MSS). Pide charizard y verás la respuesta llegar en varios pedazos.

              

              

                
¿Quién cierra primero?

                
Tu servidor llama a Close() apenas termina de escribir, así que él envía el primer FIN. Por eso es el servidor el que queda en TIME_WAIT: un detalle que importa cuando reinicias el servidor y el puerto parece ocupado.

              

            

          


          

            

              

                
Un servidor TCP mínimo en C++


#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <cstring>

int main() {
  int server = socket(AF_INET, SOCK_STREAM, 0);
  int yes = 1;
  setsockopt(server, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes);

  sockaddr_in addr{};
  addr.sin_family = AF_INET;
  addr.sin_port = htons(1234);          // ¡orden de red!
  addr.sin_addr.s_addr = INADDR_ANY;
  bind(server, (sockaddr*)&addr, sizeof addr);
  listen(server, 16);

  while (true) {
    int client = accept(server, nullptr, nullptr);
    char buf[4096];
    ssize_t n = recv(client, buf, sizeof buf, 0);  // puede llegar incompleto
    const char* res = "HTTP/1.1 200 OK\r\nContent-Length: 5\r\n\r\nhola\n";
    send(client, res, strlen(res), 0);
    close(client);                         // tu servidor: std::thread(task, client)
  }
}

              

              

                
Consejos

                
    
                  
  • recv puede devolver menos bytes de los que esperas. Lee en ciclo hasta tener el mensaje completo.
    • 
                  
  • Usa htons/ntohs para puertos: la red es big-endian.
    • 
                  
  • SO_REUSEADDR evita el error «Address already in use» al reiniciar el servidor.
    • 
                  
  • Revisa el valor de retorno de cada llamada. Un -1 ignorado es un bug escondido.
    •
